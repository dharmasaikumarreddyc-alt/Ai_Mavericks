# Loopora GenAI Architecture

Loopora is a governed agentic commerce system rather than a chatbot layered on checkout. **Google Vertex AI** is the serving platform for Gemini 3.8 Flash; Cloud Run authenticates to Vertex AI with a dedicated service identity and short-lived Google Cloud access tokens.

## Core control loop

```text
Customer text / optional image
        ↓
Vertex AI — Gemini 3.8 Flash perception
        ↓
Vertex AI — bounded function/tool requests
        ↓
Application-owned commerce tools
        ↓
Deterministic validator
        ↓
Validator feedback → Vertex AI repair when required
        ↓
Human confirmation
        ↓
Authenticated order flow
        ↓
Merchant evidence + model-assisted insight
        ↓
Human-reviewed merchant action
```

## Vertex AI / Gemini responsibilities

- Interpret natural-language intent.
- Extract useful cues from optional retail images.
- Request bounded planning tools.
- Rank and explain grounded candidates.
- Request a repair after machine-readable validator feedback.
- Summarize grounded merchant evidence.

## Cloud identity boundary

Production model calls do not use a Gemini API key. The Cloud Run web service is deployed with a dedicated `loopora-vertex-runtime` service account granted `roles/aiplatform.user`. The runtime obtains short-lived access tokens from the Google Cloud metadata server and calls the Vertex AI `generateContent` endpoint under the configured project and location.

For local evaluation only, developers may supply a short-lived `VERTEX_ACCESS_TOKEN` generated by Google Cloud CLI. Service-account key files are neither required nor recommended.

## Deterministic application responsibilities

- Product identity and catalog membership.
- Prices and totals.
- Inventory truth.
- Budget and dietary-tag validation.
- Authentication and authorization.
- Payment state.
- Order creation and lifecycle transitions.
- Inventory and merchant operational mutations.

## Tool boundary

The retail copilot exposes allow-listed planning capabilities such as catalog search, inventory checking, constraint validation, and substitution requests. Gemini on Vertex AI can request those capabilities, but the application validates tool names and arguments and remains responsible for execution and commerce truth.

Unknown, malformed, or unsafe calls do not gain operational authority.

## Validator and repair

A proposed basket is checked against current application data. A failed plan can produce machine-readable feedback such as an unavailable SKU or policy violation. Vertex AI may request a bounded repair, after which deterministic validation runs again. Substitutions remain proposals until the customer approves them.

## Multimodal path

Optional JPEG/PNG/WebP input is compressed client-side and bounded again on the server. Gemini on Vertex AI may extract retail cues from the image, but displayed products still have to resolve to application-owned catalog records.

Loopora does not persist uploaded images in application storage.

## Decision trace

The judge-facing trace shows:

- component owner
- requested capability
- validation result
- fallback/repair state
- elapsed time
- human approval requirement

It intentionally does not reveal model chain-of-thought.

## Graceful degradation

When Vertex AI is unavailable, deterministic catalog matching remains available and is labelled as fallback. Model failure cannot bypass price, stock, budget, authentication, or human approval controls.

## Evaluation

`npm run eval:gemini` evaluates representative and adversarial cases and verifies the runtime provider is `Google Vertex AI`. Deterministic fallback is not counted as successful live-model quality. Offline application checks are kept separate from live Vertex AI evaluation so synthetic/control evidence is not presented as model-quality evidence.
